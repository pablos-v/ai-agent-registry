# Политика: контроль человека над агентом

Сквозное правило контура: **агент читает свободно, изменяет — только с подтверждением.**

## Схема мутирующей операции

```
1. ПЛАН            агент формулирует, что собирается сделать, человеческим языком
2. ПРЕДПРОСМОТР    перечисляет конкретные объекты, которых коснётся изменение
3. ПОДТВЕРЖДЕНИЕ   человек подтверждает или отклоняет
4. ИСПОЛНЕНИЕ      типизированная операция, не произвольная команда
5. ВЕРИФИКАЦИЯ     агент перечитывает состояние системы и сверяет с ожидаемым
6. АУДИТ           запрос, план, подтвердивший, результат и дельты — в журнал
```

Шаги 1–3 нельзя пропустить «потому что операция простая». Ровно на этом рассуждении
произошёл инцидент, описанный в [bulk-operations.md](bulk-operations.md).

## Пороговая автономность

Полная автономность и полное ручное подтверждение — одинаково плохие крайности:
первая небезопасна, вторая обесценивает автоматизацию. Рабочая модель — порог:

| Условие | Режим |
|---|---|
| Операция только читает данные | автономно |
| Изменение, все проверки пройдены, объём ниже порога | автономно, с отчётом постфактум |
| Изменение выше порога, любая непройденная проверка, низкая уверенность классификации | план и ожидание подтверждения |
| Тип задачи не входит в белый список | не выполняется, эскалация человеку |

Порог задаётся конфигурацией, а не зашит в код: для разных процессов он разный.

## Что делает человек, а не агент

- Принимает решение по операциям выше порога.
- Разбирает случаи, где проверки разошлись с ожиданием.
- Проверяет, что автоматика не начала «тихо» ошибаться: выборочный разбор журнала.

## Почему верификация обязательна

Успешный ответ API не означает, что данные изменились так, как задумано. После исполнения
агент перечитывает состояние и сверяет фактические дельты с ожидаемыми — расхождение
поднимает алерт человеку, а не тонет в логах.
